# Silero VAD 入力ウィンドウ方式の実測比較検証(P0-1)

## 背景

`SileroVadDetector`は、公式実装(512サンプルhop・64サンプル文脈・非重複ウィンドウ)とは異なる
ウィンドウ方式(480サンプルhop・576サンプル連続スライディングウィンドウ)を採用している。
これはこのアプリの音声取得ループが30ms(480サンプル)周期で動いており、公式仕様の512サンプル単位とは
端数が合わないための設計判断だった。

コードレビュー(GitHubレビューP0-1「Silero VADの入力方式を最優先で再検証」)の時点では、
「Silero VAD自体は連続音声にロバストな設計であり実用上の精度に大きな影響は無いと考えられるが、
モデルが学習時に見ていない入力分布(重複96サンプル vs 公式64サンプル)を与え続けていることになり、
これは実際の音声で確率曲線を比較しない限り白黒つけられない」という理論上の懸念にとどまっていた。
本ドキュメントは、その懸念を実測で検証した結果をまとめる。

## 検証方法

- `SileroVadDetector`に`useOfficialWindowing`パラメータを追加し、同一クラス内で
  アプリ既定方式(`false`、本番で使用)と公式方式(`true`、この検証専用)を切り替えられるようにした。
- `LoopbackRecorder.Tests/VadWindowingComparisonTests.cs`で、同じ音声ファイルを両方式に
  まったく同じチャンク列・同じタイミングで通し、以下を比較した:
  1. 発話確率曲線(30msごとの値)の最大差・平均差
  2. `VoiceActivitySegmenter`(既定パラメータ: EnergyThreshold=0.5, HysteresisRatio=0.6)を通した
     結果の検出区間数
  3. 区間ごとの開始/終了時刻のズレ
- テスト音声: `LoopbackRecorder.Tests/TestData/generate-test-audio.ps1`が
  PowerShell(`System.Speech.Synthesis.SpeechSynthesizer`)で生成する、日本語TTS音声
  (「こんにちは、今日はいい天気ですね。」「それではゲームを始めましょう。」の2発話、無音を挟む)を
  ベースに、以下6条件で比較した(初回検証時はsample1.wav 1本のみだったが、レビュー指摘を受けて
  小声・早口・ノイズ・BGM・英語の5条件を追加した):
  - `sample1.wav`: 通常(Rate=0, Volume=100)
  - `sample2_quiet.wav`: 小声(Volume=30)
  - `sample3_fast.wav`: 早口(Rate=+6)
  - `sample4_noisy.wav`: ホワイトノイズを合成(相対振幅0.05)
  - `sample5_bgm.wav`: ゲームBGM風の低音(110/146.83/164.81Hzの合成トーン)を合成(相対振幅0.08)
  - `sample6_english.wav`: 英語音声("Hello, it's a nice day today." "Let's start the game.")
- `VadWindowingComparisonTests`は現在、以下の許容閾値を超えた場合にテストを失敗させる
  regression assertionを備えている(初期実装ではConsole出力のみで、閾値を超えてもテストは
  常に成功する状態だったが、レビュー指摘を受けて修正した):
  - 確率曲線の平均差 < 0.05
  - 検出区間数の差 ≤ 1
  - 区間ごとの開始/終了時刻の差 ≤ 100ms

## 結果

| ファイル | 条件 | 確率曲線の最大差 | 確率曲線の平均差 | 検出区間数(既定/公式) | 境界時刻の最大ズレ |
|---|---|---|---|---|---|
| sample1.wav | 通常 | 0.4301 | 0.0115 | 2件 / 2件(完全一致) | 30ms |
| sample2_quiet.wav | 小声 | 0.4633 | 0.0152 | 2件 / 2件(完全一致) | 60ms |
| sample3_fast.wav | 早口 | 0.5456 | 0.0430 | 1件 / 1件(完全一致) | 0ms |
| sample4_noisy.wav | ノイズあり | 0.8123 | 0.0188 | 2件 / 2件(完全一致) | 30ms |
| sample5_bgm.wav | BGM混入 | 0.5623 | 0.0189 | 2件 / 2件(完全一致) | 30ms |
| sample6_english.wav | 英語 | 0.6459 | 0.0209 | 2件 / 2件(完全一致) | 30ms |

全ファイルとも許容閾値(平均差<0.05、区間数差≤1、境界差≤100ms)の範囲内で、
`VadWindowingComparisonTests`はすべてパスしている(2026-08-21実行)。

区間ごとの詳細(通常条件 sample1.wav):

```
区間1: 開始差=0ms   終了差=-30ms (既定: 00:00.12-00:03.06, 公式: 00:00.12-00:03.09)
区間2: 開始差=-30ms 終了差=0ms   (既定: 00:03.39-00:05.67, 公式: 00:03.42-00:05.67)
```

早口条件(sample3_fast.wav)の平均差0.0430は、6条件中もっとも閾値(0.05)に近い値だった。
ただし検出区間数・境界時刻は既定/公式で完全一致しており、実用上の判断への影響はない。

## 結論

**現行の実装(480サンプルhopのスライディングウィンドウ方式)を維持する。公式方式への切り替えは不要と判断する。**

根拠:

- 6条件すべてで、検出される発話区間の**件数が完全に一致**しており、「発話として検出するかどうか」
  という最終的な判断は両方式で変わらなかった。
- 境界時刻のズレは最大60ms(小声条件)にとどまり、実際の字幕/翻訳表示のユーザー体験に
  影響する水準ではない。
- 確率曲線の差は、通常発話に対しノイズ・BGM混入・早口の条件でやや大きくなる傾向が見られたが
  (最大差はノイズ条件で0.81まで拡大)、いずれも設定した許容閾値の範囲内であり、
  `VoiceActivitySegmenter`の`HysteresisRatio`による緩衝もあって、最終的な区間検出結果には
  影響していないことが確認できた。

以上により、コードレビュー時点の「実用上の精度に大きな影響は無いと考えられる」という判断は、
TTS1本のみだった初回検証時点よりも広い条件で実測により裏付けられた。

## 限界・今後の検証余地

- 今回の検証はいずれも同一のTTS音声素材をベースにした合成音声(音量・速度・合成ノイズの
  重ね合わせ)であり、実際のマイク環境(実況者の声質・部屋の反響・実機のゲーム音源・
  Discord通話の圧縮ノイズなど)そのものでの検証ではない。もし将来的にVADの誤検出・検出漏れが
  実運用で報告された場合は、該当の音声を`LoopbackRecorder.Tests/TestData/`に追加し、
  `VadWindowingComparisonTests`を再実行することで同様の実測比較ができる。
- 早口条件の平均差(0.0430)が閾値(0.05)に近かったことから、今後さらに極端な早口や、
  複数話者が重なるケースでは閾値を超える可能性がある。閾値を超えた場合は、まず
  `MaxAllowedMeanAbsDiff`等の閾値設定が厳しすぎないか確認したうえで、それでも許容できない
  差であれば`SileroVadDetector`の`useOfficialWindowing=false`側の実装を見直すことを検討する。
- `SileroVadDetector`の`useOfficialWindowing`パラメータはテスト専用であり、本番の
  `AudioPipeline`からは常に既定値(`false`)で呼び出される(変更なし)。
